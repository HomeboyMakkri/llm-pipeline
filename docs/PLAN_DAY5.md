# План Day 5 — многошаговая LLM-цепочка

Задание: [`tasks/day05.md`](../tasks/day05.md). Исходный контракт: [`SPEC.md`](../SPEC.md). Эталонные входы: [`day4_cases.json`](day4_cases.json).

**Один пронумерованный шаг — один отдельный запрос.** Отмечаем шаг только после проверки его критерия готовности. Ниже — предлагаемый контракт, не описание реализованного поведения.

## Цель и поток данных

Штатный CLI читает исходный текст один раз и выполняет пять последовательных вызовов модели. Между вызовами передаются проверенные данные, а не сырой ответ модели:

| Этап | Что получает | Что возвращает |
|---|---|---|
| 1. Извлечение смысла | Исходный текст | Основной смысл и важные детали из текста, без классификации и ответа автору |
| 2. Классификация | Исходный текст и результат извлечения | `category` из пяти меток Day 4 и `intent` |
| 3. Структурирование | Исходный текст, извлечение и классификацию | `summary`, `sentiment`, `key_points` |
| 4. Ответ | Исходный текст, извлечение, проверенный `intent`, структурированные поля и одну инструкцию по `category` | Только `final_answer` |
| 5. Самопроверка | Исходный текст, извлечение, классификацию, поля и `final_answer` | `passed` и список `issues`: противоречия или упущения |

Исходный текст остаётся доступен на всех этапах: промежуточное извлечение может пропустить деталь. Схема проверяет формат ответа, а самопроверка — модельная оценка содержания, не гарантия точности. После положительного вердикта CLI печатает те же шесть полей, что в Day 4. Отрицательный вердикт завершает запуск без частичного результата; автоматическое исправление, повторные попытки и fallback не добавляем в Day 5.

## 1. Подготовить извлечение смысла

> Выполни только шаг 1 из `docs/PLAN_DAY5.md`: добавь схему и промпт извлечения смысла, проверь их локально и остановись.

- [ ] Добавить строгую схему с непустым `meaning` и списком непустых строк `important_details`. Разрешить пустой список деталей: не заставлять модель придумывать их. В отдельном промпте запросить один JSON-объект, не просить категорию, намерение или итоговый ответ. Исходный текст передавать без изменений. CLI пока не менять.
- **Готово, когда** локальные тесты подтверждают передачу многострочного текста, соответствие примера схеме и отклонение неверных типов и пустого `meaning`. Запросов к DeepSeek — 0.

## 3. Разделить структурирование и итоговый ответ

> Выполни только шаг 3 из `docs/PLAN_DAY5.md`: добавь независимые контракты структурирования и ответа, проверь передачу результатов и остановись.

Для общего вопроса разрешить общие знания, если они не противоречат тексту; не путать отсутствие ответа в источнике с отсутствием вопроса.

## 4. Подготовить отдельную самопроверку

> Выполни только шаг 4 из `docs/PLAN_DAY5.md`: добавь схему и промпт самопроверки, проверь их локально и остановись.

- [ ] Попросить сверить структурированные поля и ответ с исходным текстом: найти противоречия и потери деталей, существенных для задачи автора. Извлечение и классификация помогают проверке, но не заменяют источник. Для замечания указать, что именно расходится с текстом или какой важной детали не хватает. Не просить модель переписывать ответ.

## 6. Проверить полный цикл через DeepSeek

> Выполни только шаг 6 из `docs/PLAN_DAY5.md`: прогони шесть выбранных входов через штатный CLI, оцени результат и зафиксируй число запросов. Остановись после проверки.

- [ ] Переиспользовать `support_1`, `feedback_1`, `complaint_1`, `sales_2`, `general_question_1`, `general_question_2` из Day 4. Набор охватывает все категории, эмоциональный технический вопрос, прямой вопрос с ранее зафиксированным отказом и текст без запроса. Не менять эталон по результатам модели.
- [ ] Для каждого входа записать, какие этапы завершились, совпала ли категория, сохранились ли смысл `intent` и важные детали, выполнен ли эталонный признак ответа и согласуется ли вынесенный вердикт с ручной оценкой. Зафиксировать модель, неуспешные случаи и число реальных запросов отдельно от локальных проверок. Шесть полных запусков — 30 запросов без повторов; они расходуют баланс.
- Если самопроверка отклонила результат, фиксировать этап, вердикт и доступную причину из `stderr`; недоступные для ручной оценки поля отметить как «не оценено», не раскрывая отклонённый ответ через штатный вывод.
- **Готово, когда** все шесть входов обработаны без ручных подстановок между этапами, все пять этапов наблюдаемы и есть фактические результаты по каждому входу. Если часть входов не прошла полный цикл, явно указать это и не считать критерий задания о полном цикле достигнутым, пока успешных полных запусков меньше пяти.
