# Спецификация

## Назначение

Учебный Python-проект для изучения LLM API и построения пайплайна обработки текста. Общее задание и критерии по этапам находятся в `tasks/overall.md` и `tasks/day01.md`–`tasks/day07.md`.

## Текущие решения

- Первый провайдер — DeepSeek через совместимый API; клиент использует библиотеку `openai` и загружает `.env` через `python-dotenv`. Настройки: `DEEPSEEK_API_KEY`, `LLM_BASE_URL` и `LLM_MODEL`. Клиент и CLI проверены локально с подставным транспортом и реальными запросами в Day 2.
- Виртуальное окружение находится в `.venv` в корне проекта; README описывает установку в него и текущее состояние проекта.
- Проект развивается по дням; функциональность следующих дней не считается реализованной заранее.
- Dev-зависимость `pyright` проверяет `src/` и `tests/` в режиме `strict` для Python 3.10. Проектное расширение omp блокирует обычное завершение основной сессии при ненулевом результате проверки или невозможности её запустить.

## День 1

Программа принимает произвольный текст без изменения исходного кода и обращается к модели. Ожидаемый результат содержит краткое содержание, три ключевые мысли и короткий полезный ответ; его можно просмотреть в читаемом структурированном виде.

Запуск: `python -m llm_pipeline.main`. Программа читает текст из стандартного ввода до конца потока и выводит ответ модели в стандартный вывод.

Вызов API, шаблон промпта и сборка программы разделены. Подготовлены три примера и выполнены реальные прогоны в Day 2.

## День 2 — исходный контракт промпта

`prompts.py` формирует список сообщений: `system` задаёт общие правила опираться на исходный текст и не выдумывать факты; `user` содержит инструкцию и полный исходный текст. `build_prompt(text)` подставляет текст без обрезки и повторной интерпретации фигурных скобок. `get_response(messages)` передаёт готовый список в `chat.completions.create` и возвращает текст первого ответа; при отсутствии текста возбуждает `ValueError`. Инструкции не находятся в клиенте.

В Day 2 `USER_PROMPT_TEMPLATE` использовал выбранный каркас C и запрашивал три раздела по порядку: «Краткое содержание» не более 60 слов, «Ключевые мысли» — ровно три нумерованных пункта, «Итоговый ответ» — одно или два предложения.

Локальные проверки CLI с `httpx.MockTransport` подтвердили порядок сообщений, требования шаблона, передачу полного многострочного ввода с кириллицей и фигурными скобками и вывод подставного ответа; это не проверка провайдера.

В Day 2 выполнены 12 реальных запросов DeepSeek (`deepseek-flash`) для сравнения A/B/C и контроля Day 1 на `kolobok.txt`, `3pigs.txt` и `pismo_tatiane.txt`. Ручная оценка учитывала факты, структуру, самостоятельность мыслей, краткость и полезность; выбран C, поскольку в его трёх ответах не обнаружено фактических ошибок, в отличие от A и B. Затем выполнены три реальных запроса через итоговый CLI с ограничениями: все ответы соблюли числовые требования, но ответ на письмо содержал фактическую ошибку, отсутствовавшую в ответе C до ограничений. С ограничениями проверялся только C; один прогон не доказывает стабильности или причинного влияния ограничений. Точные шаблоны, результаты и ограничения сравнения — в `docs/PLAN_DAY2.md`.

## День 3 — структурированный ответ в CLI

`schemas.py` определяет `ModelResponse` на Pydantic 2. Все пять полей обязательны. `summary`, `category`, `sentiment` и `final_answer` имеют тип `str`, а `key_points` содержит ровно три строки. Строгий режим отключает приведение типов.

Локальная проверка схемы приняла корректный объект и отклонила 13 некорректных. Результаты перечислены в пункте 1 [плана Day 3](docs/PLAN_DAY3.md). Запросов к DeepSeek — 0.

`USER_PROMPT_TEMPLATE` запрашивает один JSON-объект с пятью полями схемы без Markdown-обёртки и пояснений вокруг объекта. Пример показывает четыре строковых поля и массив из трёх строк. Лимит в 60 слов для `summary` и требование одного или двух предложений для `final_answer` заданы в промпте. Сообщение `system` требует опираться на исходный текст.

Локальная проверка с `httpx.MockTransport` подтвердила порядок `system` и `user`, передачу требований к формату и содержанию, соответствие JSON-примера схеме и полную передачу многострочного ввода с кириллицей и фигурными скобками. Запросов к DeepSeek — 0.

CLI разбирает строку из `get_response` через `json.loads` и проверяет полученное значение через `ModelResponse.model_validate`. При успехе он печатает все пять полей в `stdout`, нумерует ключевые мысли, выводит итоговый ответ отдельным блоком и завершается с кодом `0`.

При ошибке разбора или нарушении схемы CLI завершается с кодом `1`, оставляет `stdout` пустым и выводит короткую диагностику в `stderr`. Для ошибки схемы указывается поле из первой ошибки валидации, если оно известно. Код завершения, оба потока и тексты диагностики проверены в семи локальных прогонах с подставным ответом. Запросов к DeepSeek — 0.

Штатная точка входа CLI прошла пять локальных прогонов с `httpx.MockTransport`: `kolobok.txt`, `3pigs.txt`, `pismo_tatiane.txt`, `support_request.txt` и `product_review.txt`. Для каждого файла проверены полный текст в запросе, код `0`, пустой `stderr` и отображение всех пяти полей подставного ответа. Команда, признаки ожидаемого вывода и результаты приведены в пункте 4 [плана Day 3](docs/PLAN_DAY3.md#4-подготовить-пять-входов-и-проверить-cli-локально). Запросов к DeepSeek — 0.

Отдельный реальный прогон через штатный CLI на этих же пяти входах: `deepseek-flash`, пять запросов к DeepSeek, по одному на файл, все с HTTP 200. Все пять ответов разобраны как JSON и прошли `ModelResponse`; для каждого запуска получены код `0`, все пять полей в `stdout` и отсутствие диагностики CLI в `stderr`. Ручная проверка выявила неточности содержания, в том числе в объяснении причины письма Татьяны. Результаты по входам — в пункте 5 [плана Day 3](docs/PLAN_DAY3.md#5-проверить-пять-примеров-на-deepseek). Этот прогон не гарантирует точность содержания и стабильность формата будущих ответов.

## День 4 — классификация и маршрутизация в CLI

В `schemas.py` модель Pydantic `ClassificationResult` в строгом режиме проверяет два обязательных поля. `category` принимает только `support`, `feedback`, `complaint`, `sales` или `general_question`. `intent` — строка с хотя бы одним непробельным символом. Назначение категорий и правило выбора по главной цели автора описаны в [шаге 1 плана Day 4](docs/PLAN_DAY4.md#1-задать-категории-и-контракт-классификации); схема проверяет формат, а не смысл классификации.

Локальные тесты схемы приняли все пять меток и отклонили семь некорректных объектов. Запросов к DeepSeek — 0.

`build_classification_messages(text)` помещает определения пяти категорий, правила выбора по главной цели автора и инструкцию вернуть один JSON-объект без обёртки в `system`, а неизменённый исходный текст — в `user`. Если явного запроса нет, промпт просит зафиксировать это в `intent`. Два локальных теста pytest проверили разделение сообщений, сохранение исходного текста, наличие всех меток и соответствие JSON-примера схеме. Запросов к DeepSeek — 0.

`build_generation_messages(text, classification)` принимает проверенный `ClassificationResult` и выбирает одну инструкцию для `final_answer` по таблице `ROUTE_INSTRUCTIONS`. Общий формат `system` требует один JSON-объект с полями `summary`, `sentiment`, `key_points`, `final_answer` без повторной классификации; в `user` передаются исходный текст и проверенный `intent`, но не метка категории. Два локальных теста pytest подтвердили, что при смене каждой из пяти категорий меняется только инструкция маршрута, а JSON-пример сохраняет четыре поля. Запросов к DeepSeek — 0.

Штатный CLI читает `stdin` один раз и отправляет запрос генерации только после разбора JSON и проверки `ClassificationResult`. Вывод появляется только после проверки ответа генерации строгой схемой `GenerationResult`: категория и намерение берутся из классификации, остальные четыре поля — из генерации. Ошибка JSON или схемы завершает CLI с кодом `1`, диагностикой этапа в `stderr` и пустым `stdout`. Пять успешных и четыре ошибочных сценария проверены через `httpx.MockTransport`; результаты — в [шаге 4 плана Day 4](docs/PLAN_DAY4.md#4-связать-классификацию-и-генерацию-в-cli). Запросов к DeepSeek — 0.
