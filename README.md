# LLM Text Pipeline

Учебный проект по созданию пайплайна обработки текста с помощью LLM. Программа связывает промпт и клиент DeepSeek; клиент и штатный CLI проверены реальными запросами в [Day 2](docs/PLAN_DAY2.md). Задания находятся в [`tasks/`](tasks/), текущие решения — в [SPEC.md](SPEC.md), план первого дня — в [docs/PLAN_DAY1.md](docs/PLAN_DAY1.md).

## Окружение

Требуется Python 3.10 или новее. Команды выполняются из корня проекта. Виртуальное окружение находится в `.venv`; если его нет, создайте:

```bash
python3 -m venv .venv
```

Активируйте окружение и установите проект с зависимостями:

```bash
source .venv/bin/activate
python -m pip install -e .
```

В Windows PowerShell для создания и активации используйте:

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -e .
```

Проверить установку без запроса к API:

```bash
python -c "import openai, dotenv, llm_pipeline; print('Зависимости доступны')"
```

Для выхода из окружения выполните `deactivate`.

## Проверка типов

Из корня проекта с активированным `.venv`:

```bash
python -m pip install -e '.[dev]'
python -m pyright
```

Версия Pyright закреплена в `pyproject.toml`. Он проверяет `src/` и `tests/` в режиме `strict` для Python 3.10 и не обращается к DeepSeek.

Проектное расширение omp загружается при запуске сессии из корня репозитория. Перед завершением основной сессии оно запускает ту же проверку через `.venv`: ошибки типов или сбой запуска возвращают диагностику агенту и блокируют завершение до успешной проверки. Подагенты не получают событие `session_stop`; пользователь по-прежнему может прервать сессию. Если сессия была открыта до появления расширения, запустите её заново.

## Конфигурация DeepSeek

Скопируйте `.env.example` в `.env` в корне проекта (`cp .env.example .env` в Linux/macOS или `Copy-Item .env.example .env` в PowerShell). Укажите ключ DeepSeek в `DEEPSEEK_API_KEY` локально, не передавая его в чат и не добавляя в Git. `.env` исключён из Git. `LLM_BASE_URL` и `LLM_MODEL` задают адрес API и модель; при необходимости их можно изменить.

Клиент `llm_pipeline.llm_client.get_response(messages)` загружает `.env` через `python-dotenv`, отправляет готовый список сообщений и возвращает текст первого ответа; если текста нет, возникает `ValueError`. `prompts.py` формирует сначала `system` с правилами опираться на исходный текст и не выдумывать факты, затем `user` с задачей и полным исходным текстом. Переменные, уже заданные в окружении, имеют приоритет. Запросы к API расходуют баланс. Команда проверки установки выше к API не обращается.

Пользовательский шаблон на основе варианта C отделяет инструкцию от входа и запрашивает разделы в порядке: «Краткое содержание» — не более 60 слов, «Ключевые мысли» — ровно три нумерованных пункта, «Итоговый ответ» — одно или два предложения. Локальная проверка CLI с подставным HTTP-транспортом подтвердила передачу требований и полного многострочного текста, в том числе с фигурными скобками, и вывод подставного ответа.

В эксперименте на `kolobok.txt`, `3pigs.txt` и `pismo_tatiane.txt` вариант C выбран по ручной оценке фактов, структуры, самостоятельности мыслей, краткости и полезности: до ограничений в его трёх ответах не обнаружено фактических ошибок. Затем три реальных запроса через CLI соблюли ограничения длины и числа мыслей, но ответ на письмо содержал фактическую ошибку. Проверялся только C с ограничениями; отдельные прогоны не доказывают стабильности. Подробности и сравнение — в [плане Day 2](docs/PLAN_DAY2.md).

## Запуск

Из корня проекта с активированным окружением выполните:

```bash
python -m llm_pipeline.main
```

Введите текст и завершите ввод: в Linux/macOS нажмите Ctrl+D на новой строке, в Windows — Ctrl+Z и Enter. Можно также передать текст из файла:

```bash
python -m llm_pipeline.main < input.txt
```

Программа передаст текст модели и выведет её ответ. Запуск делает реальный платный запрос к API. Формат и фактическая точность не гарантированы: программа не проверяет и не исправляет ответ.
